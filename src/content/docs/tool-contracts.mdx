A tool contract is the vocabulary shared by the planner, the gate, and the executor.

`action_type` tells the gate *what kind of side effect* is being proposed, which
in turn selects the detectors and policy rules that apply. An unknown
`action_type` is never executed optimistically — it is treated as unevaluated
risk.

## Browser domain

Executed through Playwright against the resolved element reference.

| Action type | Side effect | Typical risk |
| --- | --- | --- |
| `BROWSER_OPEN` | Navigate to a URL | Low, unless the host is untrusted |
| `BROWSER_SNAPSHOT` | Build an accessibility snapshot | None, read only |
| `BROWSER_CLICK` | Click one element | Depends on the element's `risk_hint` |
| `BROWSER_TYPE` | Enter text into a field | High when the field is a credential |
| `BROWSER_SELECT` | Choose an option | Low to medium |
| `BROWSER_SUBMIT` | Submit a form | High, usually irreversible |
| `BROWSER_SCROLL` | Scroll the page | None, read only |
| `BROWSER_SCREENSHOT` | Capture the viewport | Low, may capture sensitive content |

## API domain

Executed through a connector rather than a browser.

| Target system | Example action | Notes |
| --- | --- | --- |
| `gmail` | Send, archive, or delete mail | Bulk operations cross approval thresholds |
| `calendar` | Create, move, or cancel events | Cancellation is hard to undo |
| `github` | Read repositories, open issues | Guards source and secret exposure |
| `stripe` | Create a sandbox payment | Sandbox only in the MVP |

`API_CALL` is the generic contract for these connectors. The connector resolves
the concrete endpoint; the gate evaluates `target`, `payload_summary`, and the
detected entities.

## File domain

| Action type | Side effect | Typical risk |
| --- | --- | --- |
| `FILE_READ` | Read a local file | High for `.env`, keys, and credential stores |

<DocCallout>
  **Read is not safe by default.** A read that exposes an API key to the model
  context is a leak, so `FILE_READ` is evaluated with the same seriousness as a
  write.
</DocCallout>

## Adding a contract

1. Define the `action_type` and the domain it belongs to.
2. Describe the side effect it produces and whether it is reversible.
3. Declare which detectors must run before it can be allowed.
4. Add the policy rules that can escalate or block it.
5. Register the executor that performs it.

Steps 3 to 5 live in AgentGate Core. The frontend only needs the vocabulary, so
it can render a [Proposed Action Preview](/docs/demo-console-ui-states) for any
contract the backend reports.
