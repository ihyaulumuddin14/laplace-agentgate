AgentGate implements **a pre-action guardrail** flow: every action an agent
wants to take passes through a fixed pipeline of steps between "the user asked
for something" and "something actually happened in the outside world." The flow
is the same regardless of which policy pack, executor, or interface is involved.

## The flow, step by step

<DocSteps>
  <DocStep title="User gives a task.">

    The user states an intent in natural language (e.g. "Send this message to
    the hotel") through the Web Chat or CLI Demo interface.

  </DocStep>

  <DocStep title="DS-led custom function-calling loop proposes a tool call.">

    Rather than a generic off-the-shelf agent framework, the MVP uses a
    purpose-built, data-science-led function-calling loop to decide on a
    concrete action — a specific tool, with specific arguments — that it
    believes accomplishes the task.

  </DocStep>

  <DocStep title="Runtime converts the tool call into an ActionRequest.">

    The proposed tool call is normalized into AgentGate's structured request
    format, so every downstream component speaks the same schema — the same
    contract that post-MVP adapters (Section 4) will later reuse.

  </DocStep>

  <DocStep title="AgentGate Core Engine evaluates the ActionRequest.">

    The request passes through the detector, policy engine, risk scoring, and
    sanitizer components, checked against the relevant policy pack(s) (see
    Policy Packs), and assigned a decision — for example <DocToken>ALLOW,
    NEED_APPROVAL, or ASK_USER</DocToken> — along with supporting reasons.

  </DocStep>

  <DocStep title="Decision Router enforces the decision.">

    The router is the single point that acts on AgentGate's decision: it either
    lets the action proceed, routes it to the Approval Queue for human sign-off,
    or stops it outright. No component downstream of the router can bypass this
    step.

  </DocStep>

  <DocStep title="Hybrid API + Browser Executor runs only when allowed.">

    Actual execution happens exclusively after the Decision Router has cleared
    the action — see Hybrid API + Browser Execution Policy below for how the
    executor chooses between the two paths.

  </DocStep>

  <DocStep title="Audit Log records the request, decision, reasons, and result.">

    Every evaluated action — allowed, blocked, or approval-gated — is logged
    with the original request, AgentGate's decision, the reasoning behind it,
    and the eventual execution result (success, failure, or not executed).
    Logged latency also feeds the Demo Console's benchmark report (raw vs.
    guarded execution time).

  </DocStep>
</DocSteps>

<DocCard title="Hybrid API + Browser Execution Policy">

Execution is hybrid by design, not browser-first or API-only:

- Real APIs are preferred where they are available and technically feasible for
  the MVP, for example the Gmail API, Google Calendar API, GitHub API, Stripe
  Sandbox, Telegram Bot API, and the local filesystem.
- Playwright-based browser tools are the fallback, used against a sandbox or
  mock dashboard when a suitable API is unavailable, closed, paid, or otherwise
  unsuitable for the demo.
- The rule is the same regardless of path: every API call and every browser
  action — whichever executor handles it — must be evaluated by AgentGate
  before it executes. The hybrid choice is an implementation detail of Step 6;
  it never bypasses Steps 3–5.

</DocCard>

<DocCard title="Why this matters">

Because every action is forced through this pipeline — regardless of whether it
ends up going to a real API or a Playwright browser action — AgentGate can
guarantee its main rule even when the underlying agent logic is unpredictable,
the task is ambiguous, or the proposed action is dangerous: nothing reaches a
live API or browser session without first passing evaluation.

</DocCard>
